Motivation

Why Build Vectis?

One-Binary Local Mode Start the entire platform locally with a single command and an embedded SQLite database.
Built for Failure Recovery Separates database truth from queue delivery so dropped connections or crashed workers can be repaired cleanly.
Untrusted Code Boundaries Treats job execution and secret access as strict security boundaries rather than afterthoughts.

Most CI/CD and job automation tools fall into one of two extremes: lightweight task runners that struggle as soon as you need multiple machines, or sprawling platforms that are painful to self-host and debug when a job gets stuck.

Vectis is designed to bridge that gap. On a single machine, vectis-local launches the entire stack in seconds using SQLite so you can submit jobs, stream live logs, and test workflows with zero external infrastructure. When you need to scale out, those exact same components can be deployed as separate services backed by PostgreSQL.

A major focus of the design is making failures obvious and recoverable. Instead of assuming the database and the work queue are always in sync, Vectis treats the database as the source of truth and uses a background reconciler to re-queue runs if a handoff is interrupted.

Technical Decisions

Why This Stack?

Each tool in Vectis was chosen to keep local development frictionless while supporting distributed deployment when needed:

Go for Operational Simplicity

Go compiles the API, CLI, workers, and local supervisor into fast, self-contained binaries. Its concurrency model is a natural fit for multiplexing log streams, managing worker leases, and coordinating background services.

SQLite Locally, PostgreSQL at Scale

New users shouldn't have to stand up a database server just to try the tool. Supporting SQLite by default makes local onboarding instant, while PostgreSQL provides the durability and concurrency needed for multi-node environments.

gRPC & Server-Sent Events (SSE)

Internal services communicate over typed gRPC and Protobuf contracts, while user-facing clients (the CLI and web UI) consume live build output over standard HTTP Server-Sent Events that work cleanly through proxies.

SPIFFE mTLS for Job Secrets

Rather than passing static credentials around, workers authenticate to the secret broker using short-lived cryptographic identities (SPIFFE), and secrets are only released to workers holding an active claim on a running task.

How It Fits Together

What Makes It Interesting?

Split Worker Architecture Separates the worker process that manages leases and status updates from the execution runtime that actually runs user commands, making it easier to swap between host and VM isolation.
Self-Healing Queue Handoffs Submitting a job records it in the database first and returns immediately; if the queue is temporarily unreachable, the reconciler automatically repairs the handoff.
Multi-Cell Execution Designed so independent execution cells can run jobs locally and report status back to a central catalog without sharing a single global database lock.
Built-In Observability Ships with OpenTelemetry tracing, Prometheus metrics, structured audit logs, and a one-command Podman reference stack for testing realistic deployments.
